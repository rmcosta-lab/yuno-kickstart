# Fase 07 — Build intake and mandate approval screens

## Objective, target user, and user-visible outcome

Let the operations coordinator submit the canonical drayage prompt and review the extracted operation/mandate draft against the typed `/v1` contracts defined in [Fase 04](../2026-08-29-04-define-p0-http-contracts/requirements.md), then explicitly approve it. The user-visible outcome: the coordinator types a natural-language request on `/intake`, sees the source prompt, the extraction policy version, the proposed route/pickup/mandate, and any validation issues; they can revise and resubmit when an issue blocks approval; and on `/mandate` they review the immutable mandate fields and must take an explicit approval action before an operation is created.

## Scope

Included:

- `/intake`: a form (source prompt + requested language) that calls the generated `useCreateOperationDraft` mutation (`POST /v1/operation-drafts`) with a client-generated `Idempotency-Key`, and renders the resulting `OperationDraftResponse` — source prompt, `extraction_policy_version`, `draft_version`, `proposed_route`, `proposed_pickup_date`, `proposed_mandate`, and `validation_issues`.
- Editable validation feedback: each `validation_issues[].field`/`message` is shown inline; the coordinator can edit the source prompt (pre-filled) and resubmit, producing a new draft. P0 has no field-level draft-editing endpoint (see [challenge-plan.md](../../decisions/challenge-plan.md): "Editing the extraction policy through an administrative screen is a future evolution, not part of P0"), so "editable" means the prompt-and-resubmit loop, not direct mutation of extracted values.
- `/mandate`: renders the approval-eligible draft's proposed mandate (price cap formatted from `maximum_amount_minor`/currency, pickup window, allowed/escalation conditions) and requires an explicit, separate approval action (not implicit on navigation) that calls the generated `useApproveOperation` mutation (`POST /v1/operations`) with `ApproveOperationRequest` and renders the resulting `OperationResponse` (operation id, mandate version, status) on success.
- Loading, empty (no draft yet), validation-error, conflict-error (`STALE_DRAFT_VERSION`, `VALIDATION_ERROR`), retry, and success states for both screens, using `ApiErrorResponse.field_issues`/`message`/`code` for safe error display.
- An injected fetch boundary so both screens are fully interactive against the real generated hooks and types without a live backend (Fase 08/10 not yet done): each hook call passes a `request` override (the existing `SecondParameter<typeof voltaFetch>` escape hatch already generated by Orval) that resolves to a small local module returning conforming `OperationDraftResponse`/`OperationResponse`/`ApiErrorResponse` fixtures, gated by `NEXT_PUBLIC_INTAKE_USE_TEST_BOUNDARY` so it is trivial to remove once Fase 10 wires the real backend.

Excluded (left to later phases per the roadmap):

- Editing `frontend/src/lib/api/generated/**` or `api/openapi.json` (Fase 04 is the sole writer).
- Any mandate rule, carrier-eligibility rule, or backend enforcement — the draft/approval boundary only forwards typed requests and renders typed responses (constitution: frontend "must not own" business rules).
- Carrier/negotiation session screens (Fase 09), evidence/recovery/audit screens (Fase 16), and outbound-call controls (Fase 20).
- Wiring these screens to a live FastAPI backend — that is Fase 10 (`pass-text-negotiation`), the first cross-layer integration phase.
- Real coordinator authentication — `approval_actor` uses a fixed demo identity constant documented as a placeholder, not a login system (no auth phase exists yet in the roadmap).
- OpenAI Realtime, Twilio, or any provider call.

Priority: P0 — one of two phases (with Fase 09) that build the frontend surfaces Fase 10 later integrates.

Assumptions:

- Fase 01's `/intake` and `/mandate` shells (`frontend/src/app/(control-tower)/{intake,mandate}/{page.tsx,fixtures.ts}`) are presentation-only placeholders this phase replaces with real form/mutation logic; their local fixture types are not a contract.
- The generated hooks' `request` parameter (already emitted by Orval for every mutation/query) is a stable, intended extension point for injecting an alternate fetcher without editing generated files.
- One draft is reviewed at a time per browser session (no multi-draft list view is required by the gate); `/intake` may still show prior submissions from local session state for context.

Risks:

- Building against real generated types before Fase 10 exists risks a boundary that quietly encodes assumptions the real backend violates. Mitigation: the test boundary returns only values shaped by the generated types themselves (no hand-authored parallel DTOs), and every response passes through the same generated types the mutation hooks declare.
- A hardcoded `approval_actor` could look like real authorization. Mitigation: label it visibly as a demo coordinator identity in the UI and note the gap in the PR body.

Fallback: if the local test-boundary module adds more complexity than it saves, fall back to manual "populate on submit" state (no hook `request` override) and note the deviation in `plan.md`/PR — the gate only requires generated types and an injected boundary, not a specific injection mechanism.

## Acceptance criteria (one coherent vertical slice)

- A coordinator can type the canonical Manzanillo→Guadalajara prompt on `/intake`, submit it, and see the returned draft's source prompt, `extraction_policy_version`, proposed route/pickup, and proposed mandate.
- A validation-error response renders `field_issues` inline against the form and lets the coordinator edit the prompt and resubmit.
- `/mandate` shows the approval-eligible draft's mandate details and blocks approval until an explicit confirm action; approving calls `useApproveOperation` and renders the resulting operation/mandate version on success, or a safe error (including `STALE_DRAFT_VERSION`) with a retry path on failure.
- Loading, empty, error, retry, and success states are all reachable and visibly distinct on both screens.
- No file under `frontend/src/lib/api/generated/**` or `api/openapi.json` is edited; no mandate/eligibility rule is evaluated in frontend code — only typed request/response rendering.

## Layer decisions

- Frontend: App Router; `/intake` and `/mandate` pages stay Server Components for layout, with the form/mutation logic in a narrow `"use client"` leaf per screen. React Hook Form + Zod (schema mirrors `CreateOperationDraftRequest`/`ApproveOperationRequest` constraints, e.g. `source_prompt` 1–10000 chars) for the intake form; TanStack Query generated hooks (`useCreateOperationDraft`, `useApproveOperation`) for remote state. shadcn/ui primitives and Tailwind per [tech-stack.md](../../project-specs/tech-stack.md).
- API/BFF, Backend/core, Data, Yuno: not applicable — no route or service is implemented in this phase; the generated client is consumed as-is.
- AI: not applicable — extraction is simulated by the injected test boundary, not called live.
- Security: `approval_actor` is a labeled demo constant, never a persisted credential; the `Idempotency-Key` is generated client-side per logical submission (not reused across distinct prompts); no `NEXT_PUBLIC_` secret is introduced.
- Visual and accessibility: labeled form fields with associated error text, visible focus states, keyboard-operable submit/approve actions, and status conveyed by icon + text + color (not color alone), consistent with Fase 01's `StatusBadge` conventions.

## HTTP contract gate

- `POST /v1/operation-drafts` — request `CreateOperationDraftRequest` (+ `Idempotency-Key` header), response `OperationDraftResponse` (201) or `ApiErrorResponse` (422 validation, 429 rate limit, etc.) — contract owned by Fase 04, consumed as-is.
- `POST /v1/operations` — request `ApproveOperationRequest`, response `OperationResponse` (201) or `ApiErrorResponse` (404 draft not found, 409 `STALE_DRAFT_VERSION`/`MANDATE_CONFLICT`, 422) — contract owned by Fase 04, consumed as-is.
- This phase defines no new route, status code, or error semantic; it only renders the existing generated types.

## Application contract gate

- Import path: `@/lib/api/generated/api` for `useCreateOperationDraft`/`useApproveOperation`, `@/lib/api/generated/models/*` for request/response/error types.
- Public symbols added by this phase: the `/intake` and `/mandate` page components (default exports, unchanged paths) and a small typed test-boundary module (exact name/location decided in `plan.md`) exporting a fetch-compatible function and its fixture data, scoped to this phase's screens only.
- Construction: mutation hooks are called with `{ data, headers }` per the generated `MutationVariables` types; no manual `fetch`/DTO construction.
- Exceptions: none thrown directly by this phase's code — TanStack Query surfaces `ApiErrorResponse` through the mutation's `error` state, rendered via existing `ErrorState`/inline field messaging.
